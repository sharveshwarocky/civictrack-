# CivicTrack

Civic issue-reporting platform — citizens report problems (roads, water, garbage, streetlights), track official progress, and hold local departments accountable. Departments get their own portal to respond, update budgets, and post completion proof.

**Stack:** React 18 · Vite 6 · TypeScript · Tailwind CSS v4 · Supabase (Postgres + Auth + Storage + Realtime) · Leaflet / react-leaflet · framer-motion · lucide-react · react-router 6

**Status: complete & working.** Live against Supabase, all mock data removed.

---

## 1. The journey (2-minute version)

CivicTrack started as a static, mock-data demo — hardcoded profiles, canned achievements, fake budgets, and no real backend. It was rebuilt into a real product:

1. Every "static" surface (achievements, My reports, sidebar identity, notifications) became **live data from Supabase**.
2. Account creation became a proper flow: **anonymous usernames**, **GPS home-area**, **onboarding**.
3. A full **government portal** (`/gov`) with org registration, admin approval, and official work updates.
4. The **Before → After** flow became real: citizen's photo = before, org's completion photo = after, with a "not completed" state until then.
5. Real budgets, real notifications, realtime updates, tightened RLS, and honest error messages.

This README is the dev journal — how it works, what was fixed, and how to run it.

## 2. Feature build-out (requirement → implementation)

| # | Original requirement | How it was implemented |
|---|---|---|
| 1 | Achievements & "My reports" were static | Computed live from `issues.user_id` per session — no more canned lists on the profile |
| 2 | Left-bottom sidebar always showed "Sharveshwar verified" | Sidebar now shows the signed-in user's real username from `profiles` |
| 3 | Random anonymous username at signup | Onboarding generates a random username (e.g. `SwiftOtter42`), **unlimited rerolls** until the user is happy, then it's locked to the account — never linked to email publicly |
| 4 | Get user location on login | Real GPS captured during onboarding (manual area picker as fallback); exact coordinates are **not persisted** for privacy |
| 5 | Organizations need their own portal | `/gov` — org register/sign-in with email + password; registrations go **pending** until an approved admin approves via the `approve_organization` RPC |
| 6 | Before → After with real photos | Citizen's uploaded photo = **before** (`cover`); org's completion photo = **after** (`aftercover`). Slider only appears when the issue is completed; otherwise shows "Not completed yet" |
| 7 | Real budgets everywhere | Org-entered sanctioned (`budget`) and spent (`spent`) values, formatted ₹ consistently — no placeholder "TBD" anywhere |
| 8 | Anonymous, untrackable chats | Random username assigned at account creation, rerollable until satisfied; email never shown in feeds, comments, or profiles |
| 9 | Home area at account creation | Onboarding asks for home area (GPS or manual) — becomes the default feed area |
| 10 | Notifications were static | Per-user `notifications` table; generated when orgs update budgets / post updates / complete work; realtime push, read-state sync, deep-links to the exact report |
| 11 | Delete duplicate / mock data | `mockData.ts` deleted; `npm run purge` empties leftover demo rows (uses the service-role key) |
| 12 | Misaligned image placeholders / stray emojis | Cover placeholders redrawn with clean labels (no emojis in the artwork), status chips realigned |

## 3. Database design (Supabase)

### Tables
| Table | Purpose |
|---|---|
| `issues` | Citizen reports. Key columns: `user_id`, `cover` (before photo), `aftercover`, `official` (org identity), `budget` / `spent`, `completionpct`, `completed_at`, `timeposted`, `created_at` |
| `profiles` | Per-user: `username` (unique), `home_area`, avatar color, onboarded flag. **Private** — never publicly readable |
| `organizations` | Org accounts: `email`, `org_name`, `department`, `role` ('org' \| 'admin'), `status` ('pending' \| 'approved' \| 'rejected') |
| `notifications` | Per-user inbox, generated by org actions |
| `follows` | user × issue follows so orgs can notify followers |
| `comments` | Issue comments with `user_id` + `username` |
| storage | `photos` bucket (public read, authenticated upload) |

### RLS model
- **Public reads** on content tables (issues, comments, follows) — feeds are public.
- **Writes require auth** (`auth.role() = 'authenticated'`).
- **Profiles private** — only the owner can read/write their own row.
- **Deletes locked down** on content tables; the purge script uses the service-role key which bypasses RLS.
- **Notifications** insertable only by approved orgs.

### RPCs (SECURITY DEFINER — caller verified server-side)
- `approve_organization(id, status)` — only an approved `admin`-role org may call.
- `post_official_update(...)` — only approved orgs may update issue status / budgets / completion proof.
- `is_org_admin()` / `is_approved_org()` — helper functions that bypass RLS to avoid policy-recursion in policies.

### Realtime
`issues`, `comments`, `notifications` are on the `supabase_realtime` publication.

### Fresh setup
1. Run `supabase/live.sql` in the Supabase SQL Editor (idempotent — safe to re-run).
2. Create the first admin auth user via **Authentication → Users → Add user** (`admin@civictrack.gov`, a password, ✅ Auto Confirm, metadata `{"role": "org"}`).
3. Insert the org row: `insert into organizations (email, org_name, department, role, status) values ('admin@civictrack.gov', 'CivicTrack Admin', 'admin', 'admin', 'approved');`
4. `npm run purge` to clear any leftover test rows.

## 4. Bugs found & fixed (the audit)

High-severity fixes worth remembering:

- **`toDbRow` leaked camelCase `createdAt` into PostgREST inserts** — would have broken live issue creation. Now mapped to `created_at`.
- **Photo upload** previously stuffed multi-MB base64 into the DB when storage failed — now aborts with a clear error.
- **Notification fan-out** could fail silently for everyone (one bad UUID row killed the batch) — now UUID-filtered and carries `issue_id`.
- **Onboarding flash** on first OTP login — profile resolution now gates the route guards so the user never lands on a blank screen.
- **Frozen relative timestamps** — `relativeTime()` derives live labels from `created_at`/`postedAt` everywhere instead of stored "x min ago" strings.
- **Optimistic writes** (upvotes, follows, reactions, comments) now revert on failure instead of lying; comments are optimistic with realtime-dedupe.
- **Org updates apply optimistically** after the RPC so work panels reflect instantly.
- **Cryptic PostgREST errors** ("Could not find the table 'public.profiles' in the schema cache") are translated by `friendlyDbError()` into actionable messages ("run supabase/live.sql"), plus a pre-flight table check shows a dismissible banner when the schema is missing.
- **Org session re-validation** on every portal load; `logoutOrg` no longer nukes a citizen's session.
- **Policy recursion** in the organizations RLS policy — fixed with `SECURITY DEFINER` helper functions.

## 9. Deploying (Vercel)

vercel.json is pre-configured for SPA routing — deep links like /gov/portal/issues resolve correctly on refresh. To go live:

1. git init + commit, then push to GitHub.
2. Install the CLI: npm i -g vercel (or use npx vercel).
3. vercel login, then run vercel from the project root (framework auto-detected: Vite).
4. In Project → Settings → Environment Variables add:
   - VITE_SUPABASE_URL — your Supabase project URL
   - VITE_SUPABASE_ANON_KEY — your anon/public key
   - VITE_SUPABASE_SERVICE_ROLE_KEY — only if you run scripts server-side (never in the client bundle)
5. vercel --prod. First make sure the Phase 1 SQL from supabase/upgrade-phase1.sql has been run — the setup banner disappears once tables exist.

CI: .github/workflows/ci.yml runs typecheck + tests + build on every push/PR to main.
